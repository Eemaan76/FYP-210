  push:

  pull_request:

  lint:
    name: lint
    runs-on: ubuntu-24.04

          node-version: '22'

  test:
    name: test
    needs: lint
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '22'
          cache: npm

      - uses: actions/upload-artifact@v4

          name: coverage
          path: coverage/lcov.info

    name: analyse
    needs: test
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - uses: actions/download-artifact@v4
        with:
          name: coverage
          path: coverage
      - uses: SonarSource/sonarqube-scan-action@v8
        env:
          SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}

  package:
    name: package
    needs: [test, analyse]
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '22'
          cache: npm
        - run: make package
      - uses: actions/upload-artifact@v4
        with:
          name: devops-pipeline
          path: '*.tgz'
          if-no-files-found: error

  audit:
    name: dependency-audit
    runs-on: ubuntu-24.04
    if: github.event_name == 'schedule'
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '22'
          cache: npm
        - run: npm ci
        - run: npm audit --audit-level=high

## 9.2 The Short Answers

### 1. Before Task 1 your coverage was "100 %". Why was that number meaningless, and what made the new one honest?
In Lab 06, the test runner executed `tools/build.js` in a separate child process via `make`. Node's built-in coverage tool (`node --experimental-test-coverage`) can only observe and instrument code that is directly loaded in-memory inside the Node process via `require()` or `import`. Because `tools/build.js` ran in a detached process, the coverage collector never saw it. The coverage table had 0 lines to measure, and mathematically 100% of 0 lines is reported as 100%, which was completely meaningless.

The new number is honest because we refactored `tools/build.js` into modular exportable functions (`renderPage()`, `main()`) and exported them. The new test file `test/render.test.js` imports `tools/build.js` directly with `require()`. This allows the Node.js coverage runner to monitor every line and logical branch executed during the test run, producing a genuine and verifiable coverage figure of 94.44%.

### 2. Paste your coverage row after Task 1 and explain each uncovered line.
```text
tools/build.js | 94.44 | 83.33 | 100.00 | 35-36
```
**Explanation of uncovered lines (35–36):**  
Lines 35–36 contain the command-line execution entry point:
```javascript
if (require.main === module) {
  process.exitCode = main(process.argv.slice(2));
}
```
When `tools/build.js` is loaded as a library by `test/render.test.js` using `require()`, `require.main === module` evaluates to `false`. Therefore, the block inside the `if` statement is never executed during in-process unit tests. This code only runs when the script is directly invoked by the shell via `make build`, making it impossible for in-process unit tests to execute those two lines.

### 3. Why must lint, test, analyse and package each be required, rather than only package?
In GitHub Actions, when jobs are connected in sequence using `needs:`, a failure in an upstream job (e.g., `lint` or `analyse`) causes GitHub to automatically **skip** all subsequent downstream jobs (`package`).  

According to official GitHub documentation, a skipped job reports its status as "Success" and does not block a pull request from merging. If only `package` were set as a required status check in GitHub rulesets, the skipped `package` job would allow the PR to merge despite earlier stages failing. Explicitly requiring each individual job (`lint`, `test`, `analyse`, and `package`) guarantees that all stages must run and succeed.

---

### 4. What does `sonar.qualitygate.wait=true` change? What would the pipeline do without it?
Setting `sonar.qualitygate.wait=true` instructs the SonarScanner CLI to pause and wait for SonarQube Cloud to evaluate the project's Quality Gate metrics. If the Quality Gate fails, the scanner exits with an error status (exit code 3), which immediately fails the `analyse` pipeline stage in GitHub Actions and blocks the merge button.

Without this setting, the scanner simply uploads the source code reports to SonarCloud and exits with a success code (exit code 0) immediately. The pipeline would turn green regardless of whether SonarQube detected critical bugs or quality failures, effectively turning SonarQube into an unmonitored dashboard rather than an active gate.

### 5. Why did the test job have to upload the coverage report as an artifact?
In GitHub Actions, each job (`lint`, `test`, `analyse`, `package`) executes on a completely separate, clean, isolated virtual machine (`ubuntu-24.04`) with its own temporary disk filesystem. The coverage report `coverage/lcov.info` generated during the `test` stage is destroyed when that virtual machine shuts down. To pass the file to the subsequent `analyse` stage running on a different virtual machine, the `test` job must upload it to GitHub's artifact storage using `actions/upload-artifact@v4`, where the `analyse` job downloads it using `actions/download-artifact@v4`.

### 6. Name the rule that caught `pageA.title === pageA.title`, and say why ESLint and your tests did not.
- **Rule Name:** **S1764** (*"Identical expressions should not be used on both sides of a binary operator"*).
- **Why ESLint missed it:** The standard `eslint:recommended` rule set does not enable the `no-self-compare` rule by default, so comparing an identifier to itself is not treated as a syntax violation.
- **Why unit tests missed it:** The newly added `isDuplicate()` function in `tools/duplicates.js` was never imported, invoked, or tested by any test file in the `test/` directory.

### 7. Your change in 7.6 had no tests at all, yet the coverage condition did not fail it. Why not?
SonarQube Cloud's default "Sonar way" Quality Gate includes an internal condition threshold: it deliberately ignores code coverage and duplication rules on pull requests that contain **fewer than 20 lines of new code**. Since `tools/duplicates.js` added fewer than 20 lines, coverage conditions were not triggered. The Quality Gate failed solely because rule S1764 identified a **Bug**, which lowered the Reliability Rating from A to D/E.
