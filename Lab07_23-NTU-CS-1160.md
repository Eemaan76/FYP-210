```yaml
name: CI

on:
  push:
    branches: [main]
  pull_request:
  schedule:
    - cron: '0 2 * * *'

jobs:
  lint:
    name: lint
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '22'
          cache: npm
      - run: make lint

  test:
    name: test
    needs: lint
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '22'
          cache: npm
      - run: make coverage
      - uses: actions/upload-artifact@v4
        with:
          name: coverage
          path: coverage/lcov.info
          if-no-files-found: error

  analyse:
    name: analyse
    needs: test
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - uses: actions/download-artifact@v4
        with:
          name: coverage
          path: coverage
      - uses: SonarSource/sonarqube-scan-action@v8
        env:
          SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}

  package:
    name: package
    needs: [test, analyse]
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '22'
          cache: npm
      - run: make package
      - uses: actions/upload-artifact@v4
        with:
          name: devops-pipeline
          path: '*.tgz'
          if-no-files-found: error

  audit:
    name: dependency-audit
    runs-on: ubuntu-24.04
    if: github.event_name == 'schedule'
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '22'
          cache: npm
      - run: npm ci
      - run: npm audit --audit-level=high
```

## 9.2 The Short Answers

### 1. Before Task 1 your coverage was "100 %". Why was that number meaningless, and what made the new one honest?
In Lab 06, the test suite (`test/build.test.js`) executed `tools/build.js` externally as a separate CLI process using Node's `child_process.execFile()`. Node's built-in coverage runner (`node --experimental-test-coverage`) instruments only files loaded in-process via `require()` or `import`. Subprocess invocations are completely invisible to the coverage collector. As a consequence, `tools/build.js` had 0 lines instrumented and was omitted from the report, leaving an illusion of "100 %" coverage based solely on the test files.  

The new coverage is honest because we refactored `tools/build.js` into modular, exported functions (`renderPage()`, `main()`) guarded by `if (require.main === module)`. The new test suite `test/render.test.js` directly requires `tools/build.js` in-process, allowing the test runner to instrument and measure every executed statement and branch directly, producing a true coverage figure of 94.44% line coverage.

### 2. Paste your coverage row after Task 1 and explain each uncovered line.
```text
tools/build.js | 94.44 | 83.33 | 100.00 | 35-36
```
**Explanation of uncovered lines:**  
Lines 35–36 contain the CLI entrypoint guard:
```javascript
if (require.main === module) {
  main(process.argv.slice(2));
}
```
When `tools/build.js` is imported by `test/render.test.js` via `require('../tools/build')`, `require.main === module` evaluates to `false`. Therefore, the body of this conditional block (which executes `main()` when invoked directly from the command line) is never traversed during in-process unit test execution.

### 3. Why must lint, test, analyse and package each be required, rather than only package?
In a staged GitHub Actions pipeline connected by `needs:`, if an upstream job fails (such as `lint` or `analyse`), all downstream jobs that depend on it (`package`) are automatically skipped. If only the final `package` job were required in repository rulesets/branch protection, a skipped job would not register as a failure. GitHub could treat the absence of a failing run for `package` as satisfying the condition, allowing code that failed earlier quality gates to be merged. Explicitly requiring `lint`, `test`, `analyse`, and `package` guarantees that every single stage must run and succeed individually before a pull request can merge.

---

### 4. What does `sonar.qualitygate.wait=true` change? What would the pipeline do without it?
Setting `sonar.qualitygate.wait=true` instructs the SonarScanner CLI to pause execution after uploading code analysis reports, actively poll the SonarQube Cloud server for the final Quality Gate computation, and exit with an error code (code 3) if the Quality Gate fails.  

Without this property, the scanner simply uploads the analysis payload and immediately exits with status 0 (success). The pipeline would remain green regardless of how many critical bugs, security vulnerabilities, or coverage deficiencies were introduced, reducing SonarQube to an ignored dashboard rather than an enforceable quality gate.

---

### 5. Why did the test job have to upload the coverage report as an artifact?
Each job in a GitHub Actions workflow executes on a fresh, isolated virtual machine runner (`ubuntu-24.04`) with an independent filesystem. The coverage report generated by `make coverage` (`coverage/lcov.info`) exists solely on the `test` runner. Because the `analyse` job executes on a completely distinct runner, it has no access to the test runner's filesystem. Uploading `coverage/lcov.info` as a GitHub artifact allows the `analyse` runner to download it via `actions/download-artifact@v4` and pass it to SonarScanner.

### 6. Name the rule that caught `pageA.title === pageA.title`, and say why ESLint and your tests did not.
- **Rule Name:** **S1764** (*"Identical expressions should not be used on both sides of a binary operator"*).  
- **Why ESLint missed it:** The default `eslint:recommended` configuration does not include the `no-self-compare` rule; ESLint focuses on syntax and common JavaScript pitfalls unless specifically augmented with additional stylistic/logic rules.  
- **Why unit tests missed it:** The newly added `isDuplicate()` function in `tools/duplicates.js` was never imported, called, or exercised by any test file in the `test/` directory.

### 7. Your change in 7.6 had no tests at all, yet the coverage condition did not fail it. Why not?
SonarQube Cloud's default "Sonar way" Quality Gate enforces coverage and code duplication conditions only on pull requests containing at least 20 lines of new code. Because `tools/duplicates.js` contained only 9 lines of code, the coverage threshold was skipped to avoid blocking trivial changes with statistical noise. However, the gate failed strictly because the Reliability Rating dropped from A to D/E due to the bug identified by rule S1764.
